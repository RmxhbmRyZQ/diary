# 隐秘日记 — 交互过程

## 基础架构

```
┌─────────────────────────┐      HTTPS        ┌──────────────────────┐
│  客户端（Web / Android） │ ◄──────────────► │  服务端（Spring Boot） │
│                         │   JSON / Cookie   │                      │
│  加密/解密在客户端完成   │                   │  仅存储密文，零知识    │
└─────────────────────────┘                   └──────────────────────┘
```

- **用户认证**：Session Cookie（`session_id`，HttpOnly / Secure / SameSite=Strict），7 天有效
- **管理员认证**：Bearer Token（`Authorization: Bearer <token>`），30 分钟有效
- **响应格式**：`{ "code": 0, "message": "success", "data": {...} }`
- **时间格式**：北京时间 ISO 8601（`2026-05-27T20:00:00+08:00`），日期 `yyyy-MM-dd`

### 请求处理流水线

```
请求 → RateLimitFilter(@Order(3)) → SessionFilter(@Order(1)) → AdminFilter(@Order(2)) → Controller
```

- **RateLimitFilter**：最后执行（Order=3），此时 SessionFilter 已设置 `userId`，可正确按用户限流
- **SessionFilter**：拦截除 `/auth/**`、`/config`、`/admin/**` 外的所有请求，验证 `session_id` Cookie
- **AdminFilter**：仅处理 `/admin/**` 路径，验证 `Authorization: Bearer` 头

## 一、注册

```
客户端                                              服务端
  │                                                    │
  │  1. GET /api/v1/config                             │
  │──────────────────────────────────────────────────► │
  │     ← { kdf: { algorithm, iterations }, limits }  │
  │                                                    │
  │  2. 生成 16 字节随机 salt                           │
  │     PBKDF2(password, salt) → authKey (256bit)      │
  │     PBKDF2(password, salt) → KEK (256bit)          │
  │     生成随机 DEK (AES-256-GCM)                      │
  │     AES-GCM-Wrap(DEK, KEK) → encryptedDek          │
  │                                                    │
  │  3. POST /api/v1/auth/register                     │
  │──────────────────────────────────────────────────► │
  │     { username, authKey, saltAuth,                  │
  │       encryptedDek, saltEnc, kdfParams }           │
  │                                                    │
  │                                         4. 校验用户名唯一性
  │                                            bcrypt(authKey) → auth_key_hash
  │                                            写入 users 表
  │                                                    │
  │     ← { user_id, created_at }                     │
  │                                                    │
  │  5. 自动登录（见下一节）                             │
```

**关键点**：
- `saltAuth` 和 `saltEnc` 使用**同一个** salt（Web 和 Android 统一）
- 服务端**永不见**明文密码——只收到 PBKDF2 派生后的 authKey，再 bcrypt 哈希存储
- `encryptedDek` 格式：`{ciphertext_base64}:{iv_base64}`，其中 IV 为 12 字节随机数

## 二、登录

```
客户端                                              服务端
  │                                                    │
  │  1. GET /api/v1/auth/recovery?username=xxx         │
  │──────────────────────────────────────────────────► │
  │     ← { salt_enc }  // 获取加密盐                   │
  │                                                    │
  │  2. PBKDF2(password, salt_enc) → authKey           │
  │                                                    │
  │  3. POST /api/v1/auth/login                        │
  │──────────────────────────────────────────────────► │
  │     { username, authKey }                          │
  │                                                    │
  │                                   4. bcrypt 比对 authKey
  │                                      生成 Session (UUID)
  │                                      Set-Cookie: session_id
  │                                      销毁该用户所有旧 Session
  │                                                    │
  │     ← { userId, encryptedDek, saltEnc,              │
  │          kdfParams, hasRecovery }                  │
  │     + Set-Cookie: session_id=xxx                   │
  │                                                    │
  │  5. PBKDF2(password, salt_enc) → KEK               │
  │     AES-GCM-Unwrap(encryptedDek, KEK) → DEK        │
  │     DEK 缓存到 sessionStorage（Web）/ 内存（Android）│
```

**关键点**：
- 步骤 1 的 `salt_enc` 获取：优先从服务端拉取（支持跨设备登录），其次从本地缓存读取
- 单会话强制：登录时销毁旧 Session，同一用户只能有一个有效会话
- 登录失败统一返回 `401 "用户名或密码错误"`（不区分用户不存在还是密码错误）
- 速率限制：单 IP 5 次/分钟

## 三、日记同步

### 3.1 同步摘要列表

```
客户端                                              服务端
  │                                                    │
  │  GET /api/v1/entries/sync                          │
  │  ?since=2026-05-30T10:00:00+08:00                  │
  │  &clientTime=2026-05-31T10:00:00+08:00             │
  │──────────────────────────────────────────────────► │
  │                                   校验 clientTime 与服务器时间
  │                                   偏差 > 5 分钟 → 400
  │                                   查询 userId 下 updatedAt > since 的条目
  │                                                    │
  │     ← { entries: [{ id, diaryDate, updatedAt }] } │
  │                                                    │
  │  客户端比对本地 IndexedDB：                           │
  │  - 服务端有、本地无 → 待拉取                          │
  │  - 服务端 updatedAt > 本地 → 待更新                    │
  │  - 本地有、服务端无（首次全量同步时）→ 本地删除          │
```

### 3.2 批量拉取详情

```
  │  GET /api/v1/entries/batch?ids=uuid1,uuid2         │
  │──────────────────────────────────────────────────► │
  │                                   仅返回 userId 匹配的条目
  │                                                    │
  │     ← { entries: [{ id, diaryDate, mood, weather,  │
  │          favorite, encryptedPayload, iv,            │
  │          version, createdAt, updatedAt }] }         │
```

**关键点**：
- `clientTime` 校验防止客户端时钟不准导致增量同步遗漏数据
- `since` 为 ISO 8601 时间戳，不传则全量同步（首次使用）
- 批量查询自动按 userId 过滤，不返回他人日记
- 日记接口**不受限流**（从通用 API 限流中排除）

## 四、创建日记（含附件）

```
客户端                                              服务端
  │                                                    │
  │  ┌─ 附件上传循环 ──────────────────────────────┐    │
  │  │ 1. 客户端加密图片文件                            │
  │  │    AES-GCM(明文图片, DEK, random_iv) → 密文    │
  │  │    SHA-256(密文) → sha256_hex                  │
  │  │                                                 │
  │  │ 2. POST /api/v1/attachments                    │
  │  │    multipart: diary_id=0000... (占位)           │
  │  │              file=密文, iv=base64, sha256=hex  │
  │  │───────────────────────────────────────────────►│
  │  │                                 3. 校验文件大小 ≤ 10MB
  │  │                                    校验 diary 所有权
  │  │                                    按用户+日记维度检查附件数
  │  │                                    存储文件到 {basePath}/{userId}/{uuid}
  │  │                                    写入 attachments 表
  │  │                                                 │
  │  │     ← { id, mime_type, sha256, created_at }    │
  │  └──────────────────────────────────────────────┘  │
  │                                                    │
  │  4. POST /api/v1/entries                           │
  │──────────────────────────────────────────────────► │
  │     { diaryDate, mood, weather, favorite,           │
  │       encryptedPayload, iv, attachmentIds }        │
  │                                                    │
  │                                   5. 创建 Entry 记录 (version=1)
  │                                      在同一个事务中：
  │                                      UPDATE attachments SET diary_id=entry.id
  │                                      WHERE id IN (attachmentIds) AND user_id=?
  │                                                    │
  │     ← { id, version: 1, createdAt, updatedAt }    │
```

**关键点**：
- 附件先上传（diary_id 用占位值 `00000000-0000-0000-0000-000000000000`），日记创建时绑定
- 附件绑定在同一事务中完成，`WHERE user_id=?` 确保只能绑定自己的附件
- 上传的 SHA-256 是**密文**的哈希，下载时通过响应头校验完整性
- 附件上传限流：单用户 60 次/分钟
- 超大附件（>10MB）返回 400

## 五、更新日记（乐观锁）

```
客户端                                              服务端
  │                                                    │
  │  PUT /api/v1/entries/{id}                          │
  │──────────────────────────────────────────────────► │
  │     { diaryDate, mood, ..., encryptedPayload, iv,  │
  │       version: 3, attachmentIds }                  │
  │                                                    │
  │                          UPDATE entries SET ...,    │
  │                            version = version + 1    │
  │                          WHERE id=? AND user_id=?   │
  │                            AND version = 3          │
  │                                                    │
  │  情况 A：affected_rows = 1                         │
  │     ← { version: 4, ... }                         │
  │                                                    │
  │  情况 B：affected_rows = 0                          │
  │     ← 409 { version: 5, updated_at }  // 冲突！     │
  │                                                    │
  │  客户端：刷新后重试                                   │
```

**关键点**：
- 服务端使用 JPQL 原子更新 `WHERE version = :version`，不做客户端信任覆盖
- 冲突时返回 `409` + 服务端最新 `version` 和 `updated_at`
- 元数据更新（`PATCH /entries/{id}/meta`）使用相同的乐观锁机制

## 六、附件下载与解密

```
客户端                                              服务端
  │                                                    │
  │  GET /api/v1/attachments/{id}                      │
  │──────────────────────────────────────────────────► │
  │                                   校验附件存在且属于该用户
  │                                                    │
  │     ← Content-Type: application/octet-stream       │
  │       Content-Disposition: attachment               │
  │       X-Content-SHA256: a1b2c3... (密文哈希)        │
  │       X-Content-IV: base64_iv                      │
  │       {密文二进制流}                                  │
  │                                                    │
  │  客户端：                                            │
  │  1. SHA-256(下载密文) 比对 X-Content-SHA256         │
  │  2. 从本地 DB 或 X-Content-IV 获取 IV                │
  │  3. AES-GCM-Decrypt(密文, DEK, IV) → 明文           │
  │  4. 渲染图片                                        │
```

**关键点**：
- `X-Content-SHA256`：用于校验下载文件完整性
- `X-Content-IV`：客户端缺失 IV 时的回退方案（跨设备查看附件）
- 附件仅返回给上传者（`WHERE user_id = ?`）

## 七、密码找回（恢复口令）

```
客户端                                              服务端
  │                                                    │
  │  ──── 步骤1：查询托管信息 ────                       │
  │  GET /api/v1/auth/recovery?username=xxx            │
  │──────────────────────────────────────────────────► │
  │                                   始终返回 200（防枚举）
  │                                   不存在 → 全空字段
  │                                   存在但未设置恢复 → 空 recovery_data
  │                                   存在且有恢复 → 完整数据
  │     ← { recovery_data, recovery_salt,              │
  │          salt_enc, challenge, challenge_iv }       │
  │                                                    │
  │  ──── 步骤2：验证恢复口令 ────                       │
  │  客户端：                                            │
  │  PBKDF2(恢复口令, recovery_salt) → recoveryKEK      │
  │  AES-GCM-Decrypt(recovery_data, recoveryKEK) → DEK │
  │  AES-GCM-Encrypt(challenge, recoveryKEK,             │
  │                   challenge_iv) → encryptedChallenge│
  │                                                    │
  │  ──── 步骤3：重置密码 ────                           │
  │  POST /api/v1/auth/recovery/reset                  │
  │──────────────────────────────────────────────────► │
  │     { username, newAuthKeyHash, newEncryptedDek,    │
  │       newSaltEnc, newKdfParams, encryptedChallenge }│
  │                                                    │
  │                              if 未设置恢复口令 → 400 │
  │                              if encryptedChallenge  │
  │                                 不匹配存储值 → 401  │
  │                              更新 auth_key_hash 等  │
  │                              销毁所有旧 Session      │
  │                                                    │
  │     ← { "密码已重置，请使用新密码登录" }              │
```

**关键点**：
- 质询-应答机制：任何人可查询托管信息，但只有持有正确恢复口令的人才能重新加密 challenge 得到匹配密文
- 不存在、未设置恢复、challenge 为空：统一返回 `400`（防用户名枚举）
- 速率限制：单 IP 5 次/分钟

## 八、修改密码

```
客户端                                              服务端
  │                                                    │
  │  1. GET /api/v1/auth/recovery?username=xxx → saltEnc│
  │  2. PBKDF2(旧密码, saltEnc) → oldAuthKey            │
  │     PBKDF2(新密码, saltEnc) → newAuthKey            │
  │     PBKDF2(新密码, saltEnc) → newKEK                │
  │     AES-GCM-Wrap(DEK, newKEK) → newEncryptedDek    │
  │                                                    │
  │  3. PUT /api/v1/auth/password                      │
  │──────────────────────────────────────────────────► │
  │     { oldAuthKey, newAuthKeyHash, newEncryptedDek,  │
  │       newSaltEnc, newKdfParams }                    │
  │                                                    │
  │                             bcrypt 验证 oldAuthKey  │
  │                             更新凭据                  │
  │                             销毁所有 Session          │
  │                                                    │
  │     ← "密码已修改，请重新登录"                        │
  │                                                    │
  │  4. 客户端清除本地状态，跳转登录页                      │
```

**关键点**：
- 使用同一个 `saltEnc` 做新旧密钥派生（saltEnc 不变）
- 修改密码后所有 Session 被销毁，需重新登录
- `oldAuthKey` 服务端 bcrypt 比对后立即丢弃，不记录日志

```
  │                                                    │
  │     ← "托管信息已设置"                               │
```

## 十、管理员接口

```
客户端                                              服务端
  │                                                    │
  │  POST /admin/login                                 │
  │──────────────────────────────────────────────────► │
  │     { username, password }                         │
  │                                                    │
  │                            admin_users 表验证        │
  │                            生成 Bearer Token (UUID)  │
  │                                                    │
  │     ← { token }                                   │
  │                                                    │
  │  后续请求均携带：                                     │
  │  Authorization: Bearer {token}                      │
  │──────────────────────────────────────────────────► │
  │  AdminFilter 验证 token 有效且未过期                  │
  │  (30 分钟 TTL，每 5 分钟清理过期会话)                  │
```

| 端点 | 说明 |
|------|------|
| `GET /admin/users` | 用户列表（用户名、注册时间、日记数） |
| `DELETE /admin/users/{id}` | 删除用户（级联删除日记、附件、Session） |
| `GET /admin/dashboard` | 概览（总用户数、总日记数、存储占用） |
| `PUT /admin/config/kdf` | 更新 KDF 参数（算法、迭代次数） |
| `PUT /admin/config/rate-limit` | 更新限流阈值 |
| `PUT /admin/config/attachments` | 更新附件限制（大小、数量） |

**关键点**：
- 管理员使用独立的 `admin_users` 表，与普通用户体系完全隔离
- 管理员无法查看任何用户明文数据
- 管理员登录与用户登录共用 IP 限流器（5 次/分钟）

## 限流策略总览

| 端点 | 维度 | 默认值 | 实现方式 |
|------|------|--------|----------|
| 登录（用户 + 管理员） | 单 IP | 5 次/分钟 | 滑动窗口 |
| 注册 | 单 IP | 3 次/小时 | 滑动窗口 |
| 恢复接口（查询 + 重置） | 单 IP | 5 次/分钟 | 滑动窗口 |
| 通用 API（日记接口除外） | 单用户 | 60 次/分钟 | 滑动窗口 |
| 附件上传 | 单用户 | 60 次/分钟 | 滑动窗口 |

超限返回 `429 Too Many Requests`，响应头含 `Retry-After: 60`。

## 密钥体系总览

```
用户密码 ──PBKDF2(salt)──► authKey ──bcrypt──► auth_key_hash (存服务端，用于登录验证)
    │
    └──PBKDF2(salt)──► KEK ──AES-GCM-Wrap──► encryptedDek (存服务端，解密日记用)
                           │
                           └──AES-GCM-Unwrap──► DEK ──AES-GCM──► 日记密文
                                                      │
                                                      └──AES-GCM──► 附件密文

恢复口令 ──PBKDF2(recoverySalt)──► recoveryKEK ──AES-GCM──► recoveryData (= 加密的 DEK)
                                       │
                                       └──AES-GCM──► encryptedChallenge (质询-应答)
```

- **DEK**：256 位 AES-GCM 密钥，注册时随机生成，永不离开客户端明文
- **KEK**：从密码派生，用于包装/解包 DEK
- **authKey**：从密码派生，用于登录验证（服务端 bcrypt 存储）
- **盐值统一**：Web 和 Android 均使用同一个 salt 派生 authKey 和 KEK
